# FFXIV Integrated App — 專案審查與優化方向

審查日期：2026-07-30
對照專案：[beherw/FFXIV_Market](https://github.com/beherw/FFXIV_Market)（React + Vite，市場價格比較工具）

---

## 一、本次已修復的故障

### 1.1 根因：Cafemaker 資料來源已停止服務

「取得清單」（生產指引頁的材料樹 / 所需材料）整塊空白的原因不在前端邏輯，而是外部 API 死掉：

| 端點 | 實測結果（2026-07-30） |
|---|---|
| `cafemaker.wakingsands.com/Item/5057` | **HTTP 530**，body = `error code: 1016`（Cloudflare 找不到來源主機），連續三次皆同 |
| `cafemaker.wakingsands.com/search?...` | **HTTP 530** |
| `cafemaker.wakingsands.com/i/005000/005057.png` | 302 轉址到 `xivapi-v2.xivcdn.com` |
| `tnze.yyyy.games/api/datasource/zh-TW/*` | HTTP 200（0.54 – 1.4 秒） |
| `v2.xivapi.com/api/*` | HTTP 200（約 1.2 秒） |
| `universalis.app/api/v2/*` | HTTP 200 |

原本 `hooks/use-xivapi.ts` 的 `fetchItem()` 只走 Cafemaker，失敗就 `throw`。
而材料樹是 `Promise.all` 遞歸建構的（`lib/recipe-tree/material-tree.ts`），
**任何一個節點拋錯 → 整棵樹的 Promise reject → `app/crafting/page.tsx` 的 catch 把 tree 留在 null → 材料樹與所需材料兩個區塊同時消失**。
同時受影響的還有：中文物品搜尋、所有物品圖示、`useItem`。

### 1.2 修復內容

| 檔案 | 變更 |
|---|---|
| `lib/xivapi-v2.ts`（新增） | XIVAPI v2 存取層。**微批次**（12 ms 視窗）把材料樹遞歸產生的大量單筆查詢合併成一次 `sheet/Item?rows=...`（單批 50 筆），另提供以 `+ItemResult` 反查配方 ID（一次可查 20 個物品，空白 = OR）。批次遇到不存在的 row 會整批 404，已加逐筆退回機制。 |
| `lib/i18n/tw-translation.ts` | 新增 `searchItemsByTwName()` / `getItemIdByTwName()`。中文搜尋改用本地 `tw-items.json`（**42,679 筆**繁中名稱），完全離線、無 CORS 風險。排序為完全相符 > 前綴相符 > 部分相符。 |
| `hooks/use-xivapi.ts` | 移除全部 Cafemaker 呼叫。名稱優先本地繁中 → XIVAPI v2 英文 → `物品 #id`；圖示走 XIVAPI v2 asset；配方主路徑 XIVAPI v2 反查 + yyyy.games 取繁中數值，備援為 yyyy.games 名稱搜尋。`fetchItem` **不再拋錯**，改回傳降級物件。 |
| `lib/recipe-datasource.ts` | 新增 `recipe_info` / `recipe_level_table` / `ingredients` / `collectability` / `item_info` 五層快取（原本建一棵樹會重複請求同一個 rlv 上百次）；`convertToRecipe` 三個獨立請求改為並行；新增 `getRecipeInfoSafe()`；名稱備援改先查本地繁中資料，省一次網路請求。 |
| `lib/recipe-tree/material-tree.ts` | `getCachedItem` 加上防護，單一節點失敗時回傳預留位置而非讓整棵樹 reject。 |
| `app/crafting/page.tsx` | 圖示不再用死掉的 Cafemaker 網址硬拼，改用 `fetchItem()` 回傳的 `iconUrl`。 |

### 1.3 順手修掉的第二個「清單」缺陷

`app/crafting/lists/page.tsx` 的 `addItemToList()` **沒有任何呼叫端** —— 頁面上寫著「前往生產指引頁面，搜尋配方並加入到此清單」，但那個按鈕從來不存在，所以製作清單永遠是空的。

另外原本的 `selectedList` 把清單物件複製進 state，按 +/- 更新數量後詳細區塊不會重繪（stale snapshot）。

| 檔案 | 變更 |
|---|---|
| `lib/crafting-lists.ts`（新增） | 清單儲存層抽出，並實作成可訂閱的 external store（含跨分頁 `storage` 事件同步）。localStorage key 與資料格式維持不變，舊資料可直接沿用。 |
| `components/add-to-list-button.tsx`（新增） | 「📋 加入清單」按鈕與下拉選單，可選現有清單或當場新建。 |
| `app/crafting/page.tsx` | 「所需材料」標題列加入該按鈕。 |
| `app/crafting/lists/page.tsx` | 改用 `useSyncExternalStore` 訂閱儲存層，`selectedList` 由 id 推導。修掉 stale snapshot 與已淘汰的 `onKeyPress`。 |

## 二、專案現況審查

### 2.1 架構總覽

```
Next.js 16（App Router, output: 'export'）+ React 19 + Tailwind 4 + TypeScript
├── 8 個靜態路由：/ /collection /crafting /crafting/lists /gearsets /settings /simulator
├── 資料來源：yyyy.games（配方）、XIVAPI v2（圖示/英文）、本地 JSON（繁中/來源/地圖）
├── 求解器：Rust WASM（ffxiv-best-craft）+ Web Worker
├── 雲端：Firebase Auth（Google）+ Firestore（配裝/收集/設定）
└── 部署：GitHub Pages（GitHub Actions）
```

**做得好的地方**

- 生產模擬器的深度是本專案的核心資產：WASM 求解器 + Web Worker、收藏品門檻、巨集匯出、配裝系統、`RecipeLevelTable` 精確參數（`progressDivider` / `qualityModifier` / `conditionsFlag`）都有正確接上。
- 選對了 yyyy.games（tnze）作為配方來源 —— 原生支援繁中，不必經過繁簡轉換。
- 材料樹遞歸有防循環（`visited`）與深度上限。
- 靜態輸出 + Firebase 的組合，把後端成本壓到零。

### 2.2 P0 — 嚴重

**① 單一 JS chunk 12.3 MB**

```
out/_next/static/chunks/0fb99b781aaa21bb.js   12,312,294 bytes
out/_next/static/chunks/ 合計                 14 MB
```

原因是大型 JSON 被 `import` 進程式碼，因此全部打進 bundle：

| 檔案 | 大小 | 被誰靜態 import |
|---|---|---|
| `data/npcs.json` | 16.9 MB | `lib/item-sources.ts:6` |
| `data/tw-items.json` | 2.1 MB | `lib/i18n/tw-translation.ts:6` |
| `data/places-zh.json` | 154 KB | `lib/item-sources.ts:7` |
| `data/nodes.json` | 377 KB | `lib/item-sources.ts:5` |
| `data/map-entries.json` | 158 KB | `lib/map-service.ts:5` |

只要進入 `/crafting`，這 12 MB 就得先下載並解析完才能互動。手機或一般網路下這是直接不可用的量級。

**② `public/data/collections_data.json` 34.8 MB**

`app/collection/page.tsx:25` 在頁面掛載時 `fetch` 整包 34.8 MB，沒有分頁、沒有壓縮、沒有快取。`out/` 總計 48 MB，也逼近 GitHub Pages 的軟性上限（建議 1 GB / 單檔 100 MB，但頻寬會很痛）。

**③ 完全沒有測試**

`package.json` 無 test script，也沒有任何測試框架。模擬器的傷害/品質公式是這個專案最不能錯的部分，卻只有 `scripts/` 下的手動 debug 腳本。Cafemaker 掛掉這種事之所以是「使用者發現」而不是「CI 發現」，根因就在這裡。

### 2.3 P1 — 中度

**④ 市場功能完全不存在（本次未動，屬 §3.2 的範圍）**

`hooks/use-universalis.ts` 有 247 行完整實作（`useMarketData` / `useMultiMarketData` / `useMarketHistory` / `useWorlds` / `useDataCenters`），**零個元件使用它**，只透過 `hooks/index.ts` 匯出。
`components/material-cost-calculator.tsx` 的價格全靠使用者手動打字（`unitPrice: 0` 初始，1,009 行裡沒有任何 Universalis 呼叫）。設定頁也沒有伺服器 / 大區選項。

**⑤ 死碼約 1,800 行**

| 檔案 | 行數 | 狀態 |
|---|---|---|
| `lib/simulator/solver-legacy.ts` | 861 | 零 import，連 `lib/simulator/index.ts` 都沒匯出 |
| `components/crafter-status-editor.tsx` | 717 | `CrafterStatusEditor` 零 import |
| `hooks/use-universalis.ts` | 247 | 零消費端（但屬「該用卻沒用」，見 §3.2） |

**⑥ 繁簡轉換是手寫字元表**

`hooks/use-xivapi.ts` 原本有約 150 字的繁→簡對照表，`lib/i18n/tw-translation.ts` 有對應的簡→繁表。這種做法必然漏字（例：`鐵`→`铁` 有，`鑄`→`铸` 沒有）。本次修復已讓中文搜尋改走本地資料而不再依賴這張表，但 `simplifiedToTw()` 仍用於名稱降級路徑。

**⑦ 沒有請求治理**

沒有節流、沒有重試、沒有 429 處理、沒有 AbortController。使用者快速切換配方時，舊請求不會取消，回來的結果可能覆蓋新狀態（race condition）。

### 2.4 P2 — 輕度

- `next.config.ts` 同時設定 webpack 與 turbopack 的 WASM 處理，Next 16 預設 turbopack，webpack 那段實際上不生效，容易誤導。
- `lib/utils/base-path.ts:28-29` 把 repo 名稱 `ffxiv-integrated-app` 寫死。
- 沒有 error boundary，任何元件拋錯就整頁白畫面。
- `README.md` 第 5 行有損壞字元（`- **� 製作清單**`），且技術棧段落寫「部署：Vercel」與實際的 GitHub Pages 不符。
- 大量 `<img>` 而非 `next/image`（靜態輸出下 `unoptimized: true`，影響有限，但 lint 一直在叫）。

## 三、對照 beherw/FFXIV_Market 的優化方向

### 3.0 兩邊的定位差異

| | 本專案 | FFXIV_Market |
|---|---|---|
| 定位 | 生產者工作台（模擬器為核心） | 市場價格查詢工作台 |
| 技術 | Next.js 16 靜態輸出 | React + Vite |
| 資料策略 | **執行時打外部 API** | **建置時打包成本地 msgpack** |
| 市場功能 | 無 | 完整（跨伺服器比價、歷史、稅率、上傳時間） |
| 模擬器 | 完整（求解器 + 巨集 + 配裝 + 收藏品） | 有，但是 drawer 形式的附屬功能 |
| 收集追蹤 | 有 | 無 |

**它們的 `src/vendor/crafting-wasm/app_wasm.js` 和本專案的 `lib/wasm/app_wasm.js` 是同一套 WASM 求解器。**
也就是說：模擬器這塊本專案並不落後，反而在 UI 完整度上領先（它們只做成側邊抽屜）。
**真正該借鏡的是「資料層策略」和「市場功能」，不是模擬器。**

### 3.1 A. 資料層改成建置時打包（投報率最高，直接解掉 P0 ①②⑤ 和 §1.5）

它們的做法（`scripts/build-*.js` → `public/data/*.msgpack` → `src/services/*Msgpack.js`）：

```
public/data/  tw-items.msgpack  zh-items.msgpack  en-items.msgpack  ja-items.msgpack
              recipes.msgpack   npcs.msgpack      places.msgpack    shops.msgpack
              obtainable-methods.msgpack  ui_categories.msgpack     equipment.msgpack
```

換成這個架構，本專案可以同時得到：

1. **材料樹從 10–12 秒變成毫秒級** —— 配方查詢不再走 yyyy.games，本地遞歸即可。這是目前最有感的體驗問題。
2. **bundle 從 12.3 MB 降到正常量級** —— 資料從 `import`（進 bundle）改成 `fetch`（進 public，可被 CDN 快取、可按需載入）。
3. **不再有「某個外部 API 掛掉就整頁空白」** —— 也就是這次事故的結構性解法。

具體步驟：

1. 新增 `scripts/build-recipe-data.js`：從 yyyy.games（或 ffxiv-datamining-cn / teamcraft 的 dump）抓全部配方 + RecipeLevelTable + 材料關係，輸出 `public/data/recipes.msgpack`。
2. 把 `data/*.json` 全部移到 `public/data/` 並改成 msgpack（`@msgpack/msgpack`），加上 `src/utils/lazyJsonLoader.js` 等價的按需載入器。
3. `lib/item-sources.ts`、`lib/map-service.ts`、`lib/i18n/tw-translation.ts` 的靜態 `import` 全部改成 async 載入 + 快取。
4. 保留現在的 API 路徑作為 fallback（版本更新後、資料還沒重打包時仍可用）。

> 注意它們 README 明講「後端需要作者手動更新新版本資料」—— 這是本地打包的代價。建議做成 GitHub Actions 定時任務自動重打包，避免變成人工負擔。

### 3.2 B. 市場功能：從零到有

它們的市場模組值得整套照抄結構：

| 它們的檔案 | 功能 | 對本專案的建議 |
|---|---|---|
| `services/universalis.js` | Universalis 封裝，含 `aggregated` 端點取日均成交量 / 均價 / 可交易性 | 擴充現有的 `hooks/use-universalis.ts`（已寫好一半，只差 `aggregated` 與消費端） |
| `components/ServerSelector.jsx` + `constants/servers.js` | 大區 / 伺服器選單（含中國區與繁中區名稱） | **加進 `/settings`**，存進現有的設定同步機制 |
| `components/MarketListings.jsx` | 現售清單，HQ/NQ 篩選 | 新增 `/market` 路由 |
| `components/MarketHistory.jsx` + `PriceHistoryChart.jsx` | 成交歷史 + 走勢圖 | 同上 |
| `components/TaxRatesDisplay.jsx` / `TaxRatesModal.jsx` | 各城市市場稅率 | 影響淨利計算，做進成本計算器 |
| `components/ServerUploadTimes.jsx` | 各伺服器資料最後上傳時間 | 讓使用者知道價格新舊，成本很低、信任感很高 |
| `utils/fetchAggregatedPricesForItemTable.js` | 表格批次抓價 | 直接對應下一項 |

**最高價值的單一整合點**：`components/material-cost-calculator.tsx` 目前要使用者手打每一項材料的單價。
把 `useMultiMarketData`（已存在）接上去，一次帶入整份材料清單的 Universalis 均價作為預設值，
再保留手動覆寫 —— 這一步就把「生產指引 + 模擬器 + 市場」串成本專案獨有的完整迴路（它們沒有收集追蹤，也沒有這麼完整的模擬器）。

### 3.3 C. 搜尋體驗

| 它們有 | 本專案現況 |
|---|---|
| `utils/chineseConverter.js` 完整繁簡轉換 | 手寫約 150 字對照表（P1 ⑥） |
| `utils/searchNormalization.js` 多關鍵字、部分比對 | 單一子字串比對 |
| `utils/searchHistory.js` + `HistorySection.jsx` 搜尋 / 瀏覽歷史 | 無 |
| `AdvancedSearch.jsx` 依部位 / 等級 / 職業進階篩選 | 僅配方頁有職業 + 等級篩選 |
| `components/OCRButton.tsx` + tesseract 截圖辨識物品名 | 無（有趣但非必要） |
| `RelatedItems.jsx` 相關物品 | 無 |

建議優先做：完整繁簡轉換（換掉手寫表）→ 多關鍵字搜尋 → 搜尋歷史。OCR 可以最後再考慮。

### 3.4 D. 請求治理（對應 P1 ⑦）

它們的 `utils/requestManager.js` 是一個很小但很完整的範本，值得直接移植：

- 最小請求間隔 500 ms
- 429 / 5xx 判定為 rate limit
- 指數退避重試（2s → 4s → 8s，上限 10s，最多 3 次）
- 全程支援 `AbortSignal`
- 失敗訊息本地化（「請求頻率過高，請稍後再試」）

搭配 `utils/lruCache.js`（有上限的 LRU，避免圖片 / 查詢快取無限成長）。
本次修復加的批次器與各層 Map 快取都是無上限的，長時間停留在頁面上會持續累積 —— 換成 LRU 是自然的下一步。

### 3.5 E. UI 與資訊架構

- **`ErrorBoundary.jsx`** —— 本專案完全沒有，任何元件拋錯就白畫面。優先度高、成本極低。
- **`Toast.jsx`** —— 本專案用 `alert()`（`app/collection/page.tsx:251`）與自製小標籤，體驗不一致。
- **`GameVersionBadge.jsx` / `VersionFooter.jsx`** —— 顯示資料對應的遊戲版本，配合 §3.1 的本地打包資料尤其必要（使用者要知道資料多舊）。
- **響應式** —— `app/crafting/page.tsx` 是 `w-80` 側欄 + `flex-1` + `w-96` 側欄的三欄固定佈局，手機上直接爆版。它們 README 強調「完全響應式（桌面、平板、手機）」。
- **`MultiItemCombinedTree.jsx` / `MultiItemListModal.jsx`** —— 多物品合併材料樹。這個正好接上本次修好的製作清單：選一份清單 → 合併算出總材料 → 一次比價。這是很自然的下一步功能。
- **`urlSlug.js` / `ItemSEO.jsx`** —— 物品頁可分享的網址。本專案所有狀態都在 React state 裡，無法分享或加書籤。

### 3.6 F. 其他可借鏡
